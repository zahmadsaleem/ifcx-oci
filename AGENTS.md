# Repository instructions

## Documentation

Keep `README.md` at the root as the project entry point. Put all other project
documentation in `docs/`. This repository instruction file stays at the root so
it applies to the whole project.

Get explicit user approval before creating a new documentation file. A request
to create or move a named document authorizes that specific action. Do not add
design notes, plans, decision records, language guides, or other documents by
default. Update existing documentation when the requested work calls for it.

Write documentation as natural, cohesive guides to the current product. Explain
how the relevant ideas fit together and use examples where they help. Do not
turn documentation into a journal: omit task histories, progress updates,
approval dates, implementation-status labels, decision logs, and transcripts of
the conversation. Keep work reports in chat. Preserve important technical
contracts and limitations without recounting how they were decided.

## Interface language

Write for someone who knows their project files are stored in a shared place or
CDE. Use files, folders, versions, and links in the main interface. Describe what
people can do and give errors a clear next step. Put storage identifiers and raw
records in expandable technical details. Keep API names, command-line flags,
file names, and developer references accurate.
